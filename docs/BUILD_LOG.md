# SPEQULA build log

A record of how this codebase was built, across one long-running Claude Code session, for whoever picks this up next (human or AI). It covers what was done, why, what was found and fixed along the way, and what's still open. It is not a replacement for `CLAUDE.md` or `/corpus` — those remain the actual authority — this is context about the *process*.

## Ground rules that shaped every decision here

The project is governed entirely by `CLAUDE.md` and the 13-file `/corpus` specification. Four prohibitions apply everywhere: never invent a financial definition, never invent a threshold or tolerance, never invent a source-system field name, never fabricate a number. Where the corpus was genuinely silent, in conflict, or a defensible interpretation still needed a human call, the finding went into `OPEN_QUESTIONS.md` — never a guess. Real secrets (DB passwords, API keys, WorkOS credentials) were always entered by the project owner directly into `.env` files or the relevant dashboard; they were never typed, viewed-and-repeated, or otherwise handled in chat.

## Sprint-by-sprint

**Sprints 0–3** (foundation, ingestion, mapping loop, financial overview / data health / exceptions) were built first, each against the corpus section it implements, with the synthetic reference dataset (a 36-month manufacturer, a 12-month consumer brand, 13 seeded data-quality defects) as the only test fixture — every row of it labelled synthetic in the data itself.

**Live infrastructure.** Partway through, the project moved from "written but never executed against a real database" to live: a Supabase Postgres project (Session Pooler, required for the schema-per-tenant `SET`/`set_config` pattern) and Supabase Storage for raw file landing. Running the existing test suite against a live database for the first time surfaced roughly a dozen real bugs that had been invisible until then — wrong column names, a missing `set_config` fix for tenant-scoped `SET`, teardown ordering issues, a `psycopg` timestamp-infinity edge case, and a genuine ingestion performance problem (per-row DB writes taking 73s for a 400-row chart of accounts) that was fixed by batching (`resolve_account_keys_batch`, multi-row `INSERT`/`UPDATE`) down to ~3s.

**Sprint 4 — Ask.** The semantic IR schema, a deterministic SQL compiler (the model never writes SQL, per the architecture's hardest invariant), seven admission-control gates, deterministic bridges (the D-059 price/volume/mix convention as an exact algebraic identity), citation assembly, and the Ask screen. Intent classification and IR generation are the only points a model is ever called — and by explicit instruction, the real model integration (`AnthropicModelClient`) was deliberately left unconfigured, a clean connection point rather than a wired-up vendor. Verified against the golden question set: 37/37 gating questions behave correctly (a real cited answer, or an honestly-explained block — never a fabricated number), 14/14 refusals refuse.

**Sprint 5 — the monthly pack.** The eight P0 pack sections, indirect-method cash flow, chart specs stored as JSON (never rasterised), and a sign-off workflow gated on open blocking exceptions. Two real findings here: building the cash flow statement surfaced that eight of its formula's leaf components (`taxes_paid`, `asset_disposals`, `debt_drawn`, etc.) have no formula or canonical class anywhere in the corpus — logged as OQ-004 rather than approximated, so the statement honestly reports what it can compute and marks the rest not-configured. A first attempt at year-to-date comparatives would have summed `ratio_of_sums` metrics (DSO, gross margin %) across months — caught before shipping, since that's exactly what invariant #11 forbids. Verified live: re-rendering a signed pack is byte-identical even after the underlying GL data is mutated afterward.

**Sprint 6 — the second profile.** `fact_channel_order_line`, `dim_channel` (seeded with D-046's seven canonical channels), the full consumer contribution-margin ladder, both revenue models, manufacturing operating metrics, and the order-file-to-books residual (reported, never resolved — the two are deliberately not reconciled). One real correction mid-build: the pre-existing synthetic generator's "marketplace" channel tag only ever drove a commission-*borne* GL cost (still fundamentally a buyout-model company selling through a fee-charging channel) — never genuine D-061 marketplace revenue. A real marketplace vertical (a company operating as the platform, earning commission from third-party sellers) was added so the "marketplace GMV is never summed into revenue" acceptance test had real data to prove itself against. A second correction: an entity-level per-unit cost calculation was initially allocated across products by volume share — caught as exactly the kind of invented allocation convention CLAUDE.md forbids, and fixed to report entity-level only, refusing rather than allocating when the corpus doesn't state how.

**Sprint 7 — pilot operations.** Tenant deletion (a soft tombstone on the registry row, since every tenant-scoped table has an unconditional foreign key to it; the audit trail of the deletion itself is deliberately never purged), a restore rehearsal (no `pg_dump`/`pg_restore` available in the sandbox, so a logical clone-and-verify mechanism was built and run against the live 18-table manufacturer schema instead), named time-bound logged employee access, and per-tenant model cost tracking (columns exist, stay null until a real model is wired up). The sprint's own "no client-specific code exists anywhere in the repository" acceptance criterion was turned into an actual structural test — which found and fixed three real hardcoded `"manufacturing"` profile defaults left over from earlier sprints. No retention *period* is invented anywhere (OQ-005): deletion is request-triggered only, never time-based, because the corpus never states one.

## Running the whole system live, end to end

The first time the frontend was opened in an actual browser (after all seven sprints were "done" on paper) surfaced four more real bugs that no unit or integration test had caught, because none of them exercises a browser:

1. **No CORS middleware on the backend at all.** Every frontend request was silently blocked by the browser. Fixed with a `CORS_ALLOWED_ORIGINS`-configurable `CORSMiddleware`.
2. **`withAuth()` missing `{ ensureSignedIn: true }`.** Per AuthKit's own docs, the default behaviour is per-page opt-in auth, not "secure by default" — so the app never actually redirected to sign-in, it just sat on a `Signing in...` placeholder forever.
3. **WorkOS was never actually finished being set up** — `.env` still held the literal placeholder text for `WORKOS_CLIENT_ID`, and once that was fixed, the running backend process needed a full restart (not just `--reload`, which only re-imports Python modules, not the shell environment the process was launched with).
4. **A fresh WorkOS Organization Membership defaults to the built-in `member` role**, not any custom role you've created — has to be explicitly reassigned per member.

Once through all four, the system worked exactly as designed: a fresh tenant with no approved mapping showed every gated metric as honestly "not available," running and freezing a real mapping version (400 real chart-of-accounts lines, 99.86% coverage by value) unlocked cash and net debt, and a balance sheet that didn't balance was correctly *not displayed* rather than shown wrong — off by exactly the value still sitting in the accounts deferred to the mapping review queue.

## What's genuinely open

See `OPEN_QUESTIONS.md` for the full, current list (format per `CLAUDE.md` section 4). As of this writing: an undeclared auto-accept rupee ceiling (OQ-001), a `debt` metric formula that disagrees with its own governing decision (OQ-002), undeclared admission-control cost/row caps (OQ-003), eight undefined cash-flow leaf metrics (OQ-004), and an undeclared tenant data retention period (OQ-005). None of these were guessed around — each blocks exactly the piece of functionality it affects, disclosed in the code at the point it bites.

Also open, by explicit instruction rather than oversight: a real `AnthropicModelClient` (the vendor call is the account owner's to make), and enforcing Ask's admission gates at the database role level via a masking view over `map_account` (attempted once, found to break the gates it was meant to protect, reverted, and documented as follow-up rather than shipped broken or silently skipped).
